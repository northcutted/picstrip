# PicStrip 1.8.0 release acceptance

Use this checklist for the exact signed 1.8.0 candidate selected for distribution. Automated checks and a successful upload do not record a device pass. See [release operations](../ci-cd/operations.md) for the commands and approval flow.

## Select and record the candidate

Select a successful **Release Prep** run from the final `main` revision, including the current localized release notes. Verify its candidate, QA evidence, checksums and provenance before using its run URL as a release input.

Record these values in the release handoff:

| Field | Required record |
| --- | --- |
| App version | 1.8.0 |
| Build number | Read from the verified candidate; do not assume an earlier build |
| Source | Full source SHA and successful Release Prep run URL |
| Binary | Verified IPA SHA-256 |
| Store assets | Packaged metadata revision and complete configured screenshot inventory |
| TestFlight | Successful upload run URL and Apple's `VALID` build identity |
| Device acceptance | Device, OS, build, date and result for each check below |

Keep that same binary through TestFlight, publication and App Store staging. If another candidate is selected, repeat the checks affected by that change and record the new identity.

## Automated release checks

- Required PR checks pass on the final head before merge, including iPhone/iPad UI smoke when selected.
- Release Prep passes native and compatibility tests, lint/localization, static analysis, signed-bundle verification, candidate verification and provenance validation.
- All configured store locales have validated text and screenshots. Review the images actually being packaged.
- The app and share extension carry the same version and build. The packaged accessibility declarations match the supported claims.

## Device acceptance before submission

On the selected TestFlight build, record the following on iPhone and iPad where applicable:

1. **Photos and shapes:** import a photo, cover details with rectangle, square, circle, oval and custom shapes, draw and edit an outline, move/resize it, undo/redo, and inspect the exported result. Confirm the intended details are covered and the surrounding picture is preserved.
2. **Sidebar and layout:** hide/restore the sidebar in a wide window, rotate or resize while a region is selected, and verify that edits and selection remain. For supported foldable hardware, exercise book/tabletop poses and changes during editing and camera use; record the device coverage actually available.
3. **Camera and video:** take a photo, record a short video with sound, check live findings, track a manual shaped cover, adjust its timing, bleep/mute speech and export. Check front/back cameras, denied microphone permission, cancellation and background/foreground transitions.
4. **Save and share:** save a new photo/video to Photos, check replace/batch operations and denied permissions, receive a cleaned PNG/JPEG/HEIC in another app, and confirm redactions and metadata removal. Check the share extension and Shortcuts handoff.
5. **Accessibility and appearance:** check Larger Text, VoiceOver editing paths, RTL, dark appearance and reduced motion. The [detailed accessibility walkthrough](1.7.1-accessibility.md) describes the spoken tasks; use this selected build rather than its historical branch/build references.
6. **Resources:** check a representative large photo, a batch and a sustained camera/video session on the oldest supported hardware available. Record any remaining device-coverage limits.

## Accessibility declarations

The existing accessibility improvements remain in the app. VoiceOver and Larger Text declarations stay `false` for iPhone and iPad until their complete device passes are recorded. [PR #63](https://github.com/northcutted/picstrip/pull/63) was closed without merging those unsupported declarations. A later declaration change needs its own evidence and reviewed candidate.

## Stage and approve

After device acceptance, use **Release → Prepare App Store submission** with the successful TestFlight run URL. Review the exact build, store text, screenshot coverage, accessibility declarations and release policy in staging.

The configured policy is release after Apple approval with phased rollout. Approve the protected production job only when ready to request Apple review. App Privacy answers, agreements and any remaining App Store Connect account questions must also be complete. A prepared or staged candidate is not an Apple approval or a public release.
